# no-stack boilerplate review · 24 November 2026

## Decision

Build the next starter from a minimal account flow on the existing pnpm/Turborepo, PostgreSQL, Drizzle, tRPC and TanStack Query foundation. Patch Next.js and upgrade Expo. Share account behavior first. Expo Router for all three platforms is the most promising architectural rewrite for this project's priorities. Vite and TanStack Router merit a separate trial for browser-heavy products. Keep one winning default to maintain.

The baseline is the verified GitHub default branch, `0e93c94`. The working checkout is `feat/chatbot` with local changes. Posts ship on main. Chat, its schema, and the required OpenAI key belong to the feature branch. Three independent reviews covered clients, GCP, and Vercel. Evidence below comes from source, lockfiles, published documentation, and the actual GitHub CI run. No application timings, fresh-project setup times, device runs or cloud deployments were measured. [Reviewed revision](https://github.com/dyl-young/no-stack/tree/0e93c941d9aa45fd40985e8d132c8d3ee05b308b)

### What a generated project should contain

One “Continue with Google” button, one empty signed-in destination, and one account screen showing the provider-supplied name and avatar with sign-out and account deletion. Offer custom profile editing and avatar uploads when a product needs them. Keep the UI controls those screens use. On main there are 50 web and 33 native UI files. A static traversal from the routes and web middleware reached 17 web and 5 native UI files. This measures source inventory. Use production bundle traces to measure download cost.

Drop posts and chat from the generated base, including routes, navigation, dependencies, seed data, migrations and AI keys. The existing branch can serve as a reference. A generated project should be ordinary editable TypeScript with no ongoing dependency on the generator.

**Use Google as the sole sign-in provider for personal projects** on web, Android and iOS development builds. The first successful Google sign-in creates the app account. Map its verified identity to a stable app user ID. Disable email/password registration and remove the password forms, confirmation emails and reset handlers. Keep the OAuth callback, session restoration, sign-out and account deletion. Revisit Sign in with Apple if a project moves toward public App Store distribution.

For credential-free first run, exercise the normal callback and session path against a local-only test identity provider. Production configuration should accept only the configured production issuers. The setup guide should distinguish this local experience from real Google login, which needs a registered OAuth client and the correct callbacks. For existing deployments, offer verified account linking before retiring passwords so existing users retain their app identities and data.

Borrow Pontus's distinction between independently deployed apps and packages with explicit exports. Today Next hosts both the website and the API consumed by Expo. Keep that single process initially. Give the tRPC router a small verified-user context and isolate the HTTP adapter. Extract a deployable API when a universal Expo client or a separately hosted SPA needs it. Put form inputs, public response types and query definitions in client-safe exports. The current validator entry point imports Drizzle and the demo post schema alongside sign-in validation. Keep database schemas and admin clients server-only. Share design tokens and account behavior. Retain platform implementations for browser focus, keyboard navigation, secure session storage and file picking. [Pontus's layout](https://x.com/pontusab/status/2124089316599386298) · [Current validators](https://github.com/dyl-young/no-stack/blob/0e93c94/packages/validators/src/index.ts)

## Framework and performance choices

**Modernize the baseline.** Main locks Next 16.3.5 and Expo 55.0.26 with RN 0.83.9. Web uses React 19.1.4 and native resolves 19.3.0. Move Next to 16.4.6, the stable patch checked for this review. The November security release landed in 16.4.5. Upgrade Expo through SDKs 56, 57 and 58 in order, following the supported React/RN pair and validating native dependencies and NativeWind preview compatibility at each step. Compare emitted bundles after the upgrade. [Next security release](https://nextjs.org/blog/november-2026-security-release) · [Next 16.4](https://nextjs.org/blog/next-16-4) · [Expo upgrade guide](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) · [Expo SDK 58](https://expo.dev/changelog/sdk-58)

**First performance candidate on the existing stack.** The web landing components request the user separately, and a request to tRPC can encounter user verification in both middleware and the API context. Count actual outbound auth requests on a cold signed-in page and on a profile mutation. Deduplicate within the request, narrow middleware where appropriate and retain authorization at the API boundary. Consider locally verified claims for reads if the issuer and signing keys support it. Keep fresh-user checks for sensitive operations. Record p50/p95 latency and confirm two-user isolation. [Middleware](https://github.com/dyl-young/no-stack/blob/0e93c94/apps/nextjs/src/utils/supabase/middleware.ts) · [tRPC context](https://github.com/dyl-young/no-stack/blob/0e93c94/packages/api/src/trpc.ts) · [Supabase claims](https://supabase.com/docs/reference/javascript/auth-getclaims)

### Applying the fast-web screenshot

- **Use the loading strategy now.** Define query options once per resource, start essential data and route code concurrently, and give secondary panels independent loading states. Use intent prefetch on likely destinations, including keyboard focus. Test direct entry and a cold tap on a phone. Scope the browser query client to its session and create server query clients per request. [TanStack preloading](https://tanstack.com/router/latest/docs/guide/preloading)
- **Use the measurement discipline now.** Trace cold sign-in, a deep link to account, warm navigation and typing in a realistic list fixture. Record Brotli bytes once per downloaded asset, auth round trips and time to usable content. Treat the screenshot's 150 kB total initial JS, 50 kB route-specific JS and 20 kB first-view CSS as trial budgets. Track field p75 LCP ≤2.5 s, INP ≤200 ms and CLS ≤0.1 when real traffic exists. Track native cold launch, route readiness and JS bundle size separately.
- **Trial Redact independently.** It replaces the browser renderer and defaults to synchronous work. The Next adapter makes a same-commit React DOM/Redact comparison possible before changing router or framework. Include typing under load, forms, dialogs/portals, Suspense, hydration and Safari. Promote only if cold entry improves materially and input latency and required behavior hold up. Its browser gains do not transfer to native rendering. [Redact compatibility](https://tanstack.com/redact/latest/docs/compatibility) · [Next adapter](https://github.com/TanStack/redact/blob/main/docs/next.md)
- **Prioritize TypeScript 7 among toolchain upgrades.** Move from the current 5.9 catalog through 6 compatibility, then measure clean and incremental typechecks with the native compiler. Check declaration paths, editor support and type-aware ESLint rules. Benchmark React Compiler independently on a representative interaction. Consider StyleX only when the compiled CSS trace identifies a worthwhile problem. It adds a web styling migration alongside today's Tailwind/NativeWind setup. Keep pnpm and the committed lockfile while testing. Try Oxlint against the existing rule set if lint dominates CI. Bun canary can be a benchmark job without becoming a prerequisite for every new project. [TypeScript 7](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) · [Vite React Compiler integration](https://vite.dev/blog/announcing-vite8)

### Portable agent features

Keep the base runnable in a plain Node container with PostgreSQL and local Turbo caching. Make that a CI smoke test with Vercel environment variables unset. Replace the current database driver selection based on VERCEL_ENV with explicit connection settings. Hosted caching, model gateways and managed workflow execution can be selected by a project.

When the first product needs an agent, start with one authenticated server endpoint that streams one result, a direct model provider, and one typed, user-scoped tool. Vercel’s open-source AI SDK fits this shape. Inject the provider explicitly, for example Vertex AI on GCP. Keep provider credentials server-side. Both clients consume the same HTTP stream. An optional example can keep state in memory for the request and cancel on disconnect. Introduce stored history when users need to revisit it, and a durable jobs system when work must survive disconnects or process restarts. [AI SDK provider management](https://ai-sdk.dev/docs/ai-sdk-core/provider-management) · [Vertex AI provider](https://ai-sdk.dev/providers/ai-sdk-providers/google-vertex)

## A GCP path that preserves the monorepo

**Recommended pilot for a new project:** Run the current web/API service on Cloud Run, use same-region Cloud SQL PostgreSQL with Drizzle, Firebase Authentication or Identity Platform for identity, and Cloud Storage for avatars. Continue local development with PostgreSQL, the Auth emulator and a local upload implementation. Put infrastructure provisioning behind an explicit deployment choice. A fresh developer checkout should work before anyone creates a cloud project. [Cloud Run to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connect-run) · [Firebase emulators](https://firebase.google.com/docs/emulator-suite/connect_storage)

| Current coupling | What must change |
|---|---|
| The DB client uses the presence of VERCEL_ENV to select TCP and otherwise opens a Supabase-specific WebSocket proxy. | Select an explicit Postgres connection mode. Use a bounded pool and cap Cloud Run instances against the database's connection limit. [DB client](https://github.com/dyl-young/no-stack/blob/0e93c94/packages/db/src/client.ts) |
| Profile IDs reference auth.users. A database trigger provisions profiles. tRPC accepts Supabase clients and a provider user. | Preserve an app-owned UUID and map a verified issuer/subject to it. Provision the profile idempotently. Web uses a verified HTTP-only session cookie with a protected session-exchange endpoint. Native sends a verified ID token. Specify refresh, revocation and deletion behavior. Use a device-compatible Google credential flow. [Schema](https://github.com/dyl-young/no-stack/blob/0e93c94/packages/db/src/schema/profile.ts) · [Firebase session cookies](https://firebase.google.com/docs/auth/admin/manage-cookies) · [Client support matrix](https://firebase.google.com/docs/web/environments-js-sdk) |
| Avatar paths, public URLs, upload rules and deletion depend on Supabase Storage. | Issue a short-lived upload URL for a server-chosen owner-scoped object key. Finalize after verifying ownership, bytes and type, then update the profile. Store a key, allowing the delivery host to change. Ordinary HTTP uploads work on web and native. Decide read visibility explicitly. [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls) |
| Local services, migrations, deployment and grants assume Supabase. | Put provider-independent SQL migrations under one owner and deploy via a single migration job. Verify access through the API and effective database grants. Main enables the Supabase Data API for public, so inspect actual privileges before assuming the API is the only path. Realtime is disabled on main. Test real IAM and CORS in staging. [Supabase configuration](https://github.com/dyl-young/no-stack/blob/0e93c94/supabase/config.toml) · [Data API grants](https://supabase.com/docs/guides/api/securing-your-api) |

**Alternative worth comparing:** Better Auth on the same Cloud Run/PostgreSQL infrastructure gives a TypeScript-owned auth service with Expo and Drizzle support. Firebase reduces auth operations. Better Auth improves provider portability and leaves the team responsible for mail delivery, abuse protection and session operations. Ship one selected provider per project. Firestore would also change the data model, API and offline behavior without a demonstrated requirement here. [Better Auth for Expo](https://better-auth.com/docs/integrations/expo) · [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle)

**Cost and cutover:** Cloud Run can scale to zero. A running Cloud SQL instance sets an idle cost floor for each environment, plus backups, storage and HA if selected. Price the actual region, expected concurrency, active users and QA/UAT/production topology before promotion. Existing projects need a separate rehearsal: preserve IDs and OAuth links, verify password-hash imports on fixtures, plan sign-in after cutover, reconcile row counts and avatar checksums, then test the final write freeze/delta and rollback. A fresh starter can bypass the data migration. [Cloud SQL pricing](https://cloud.google.com/sql/pricing) · [Cloud Run pricing](https://cloud.google.com/run/pricing) · [Firebase identity imports](https://firebase.google.com/docs/auth/admin/import-users)

## Implementation order

1. Start from main. Repair CI, runtime pins, package outputs and account correctness. Add the two-account and deletion regressions.
2. Generate the smallest useful web/mobile project and make first-run reproducible. Measure clean setup time, dev-server readiness, auth calls, initial route bytes, and native startup on this baseline.
3. Complete account parity once. Run the universal Expo account-flow trial against that baseline. For browser-first work, benchmark the Vite/Router option and isolate any Redact gain on the same commit.
4. Run a greenfield GCP pilot after identity and storage contracts exist. Promote it once the same account suite passes on web and both native platforms, a clean local start needs no cloud credentials, and the cost and operating burden fit the intended projects.
